# 怎么合理使用子 Agent

子 Agent 是由主 Agent 临时启动的独立执行者。它拥有自己的上下文，完成限定任务后，把结果交还给主 Agent。

它最重要的作用不是“多找几个 Agent 干活”，而是把搜索、阅读、实验等过程产生的大量中间信息隔离出去，让主会话只保留真正需要的结论和证据。

## 什么场景适合使用

### 大量搜索或阅读

例如在陌生代码库中寻找一条调用链、阅读几十页官方文档，或者从长日志中定位异常。过程中会产生很多临时结果，最终只需要几个文件位置或一份简短结论。

### 多个问题可以独立调查

例如同时核对三个服务的认证方式，或分别检查前端、后端和测试中的风险。每个问题彼此独立，最后再由主 Agent 汇总。

### 需要独立验证一个假设

当讨论遇到“这个方案到底能不能运行”时，可以让子 Agent 做一个范围受限的实验，再把结果带回主会话。

### 生成独立资产

图片、数据整理结果或一次性报告等成果可以单独生成，而且不会和主 Agent 正在修改的文件发生冲突。

## 什么场景不适合使用

- 需求还很模糊，需要不断和人讨论；
- 任务很小，主 Agent 几分钟就能完成；
- 多个 Agent 必须同时修改同一文件；
- 每一步都依赖前一步的实时结果；
- 涉及最终产品取舍、权限决定或风险接受；
- 主 Agent 必须亲自看到全部原始证据。

如果子任务无法在不了解主会话全部历史的情况下独立完成，通常就不适合交给子 Agent。

## 怎么正确使用

一份清楚的委派说明至少包含五项：

```text
目标：需要回答什么问题
范围：允许查看或修改哪些内容
限制：禁止执行哪些操作
证据：结果需要附带哪些路径、行号或链接
完成条件：什么时候可以停止
```

例如：

```text
只读检查本次认证模块变更是否引入权限回归。
范围限于当前 diff 和关联测试，不修改文件，不启动其他 Agent。
按严重程度返回问题；每项附带文件、行号和具体失败场景。
如果没有发现，说明检查过的范围和仍然存在的风险。
```

子 Agent 返回后，主 Agent 还要做三件事：

1. 检查重要结论是否带有原始证据；
2. 处理不同报告之间的重复和冲突；
3. 保留最终判断、文件写入和交付责任。

## 常见误区

**任务越多，子 Agent 越多。** 并行只能缩短互相独立工作的等待时间，拆分过细反而会增加说明、等待和汇总成本。

**只要一份结论就够了。** 子 Agent 的报告是二手信息，没有文件位置、链接或实验输出，主 Agent 很难判断结论是否可靠。

**让多个 Agent 同时写同一片代码。** 这通常会带来冲突和重复验证。更稳妥的方式是一个主写入者，其他 Agent 只负责调查或生成独立成果。

**把决定也委派出去。** 子 Agent 可以准备事实和选项，但涉及需求、取舍和风险的最终决定仍应留在主会话。

## 一句话判断

如果一项工作边界清楚、可以独立完成、过程信息很多，而且最终结果能够用证据检查，就适合使用子 Agent。

期待结果返回主会话，用子 Agent；准备把整个任务交给下一会话，则应该使用 Handoff。
