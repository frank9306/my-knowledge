# 值得反复阅读的10篇 Vibe Coding 文章

我最初把 Vibe Coding 理解成一种更自然的编程入口：描述意图，让模型生成代码，再通过对话不断修正。把这十篇文章和论文放在一起重读后，我更愿意把它理解成一项环境工程。模型负责提出和执行方案，仓库、工具、隔离环境、测试与评估共同决定这些方案能否稳定落地。

这份清单来自一份对 AI 编程 Harness 资料的筛选报告。报告从 arXiv 和 OpenAlex 的去重候选、官方工程文章、论文、Benchmark 与项目资料中，按关注度、主题相关性、方法与证据、可操作性及时效性筛出十项。这里的“值得反复阅读”不是全球流量排名，也不是论文质量排名，而是我的阅读判断：它们分别补上了 Vibe Coding 从“生成代码”走向“交付软件”时最容易缺失的一块。

## 1. Harness engineering：工程师开始设计 Agent 工作的环境

**原文：** [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

OpenAI 的这篇工程复盘最适合作为入口。它记录了一个内部产品实验：代码、测试、CI、文档、可观测性和内部工具都由 Codex 生成。文章报告，项目在五个月内形成约一百万行代码、合并约 1,500 个 PR，并估计只用了手写代码约十分之一的时间。这个数字来自单个团队的自述，不能直接外推，但它揭示的工程变化比数字本身更值得注意。

团队早期的瓶颈不是 Codex 不会写代码，而是环境没有说明清楚。于是工程师的工作从直接实现功能，转向补齐 Agent 缺少的能力。他们让仓库知识可以检索，让每个 worktree 都能独立启动应用，让日志、指标、Trace、浏览器和评审结果都能被 Agent 读取，再把架构边界写成自定义 lint 和结构测试。

这篇文章值得反复读，因为它把 Harness 从一个模糊术语变成了具体对象：短 `AGENTS.md` 是地图，版本化文档是知识库，工具提供感知与行动能力，机械约束守住架构，测试和可观测性提供反馈。它提醒我，模型表现不好时，“再试一次”通常不是最有价值的修复；更应该问，环境缺少了什么可见信息、工具或约束。

## 2. Demystifying evals：先定义什么叫成功

**原文：** [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

Anthropic 把一次 Agent 评估拆成任务、试验、评分器、Harness 和评估套件。这个拆分很重要，因为 Agent 会经过多轮工具调用并改变外部状态，错误也会沿轨迹累积。只看最后一段自然语言回答，无法判断代码是否正确、工具是否越权、状态是否真的发生变化。

文章把评分器分成三类：代码评分器适合单元测试、静态分析、状态检查和工具调用核对；模型评分器适合开放式质量判断，但成本更高、结果不确定，需要人工校准；人工评分最接近专家判断，却昂贵且缓慢。实际评估通常把它们组合起来，而不是指望一种评分器覆盖所有问题。

我重读这篇时会特别检查自己的验收标准：它是在验证最终状态，还是只在验证 Agent 声称做了什么？它能区分需求修复和回归吗？它记录了轮数、工具调用、Token、延迟和人工介入吗？一旦这些问题没有答案，“通过率”就很可能只是一个缺少解释的数字。

## 3. SWE-bench：把真实 Issue 变成可执行任务

**论文与项目：** [SWE-bench: Can Language Models Resolve Real-world GitHub Issues?](https://www.swebench.com/original.html)

SWE-bench 建立了后来许多 Coding Agent 评估沿用的任务形态。它从 12 个 Python 仓库的真实 Issue 和 PR 中整理 2,294 个任务，为每个任务准备可安装的仓库状态与 Docker 环境，再用测试判断补丁是否解决问题。

它最有价值的设计不是排行榜，而是两类测试信号。`FAIL_TO_PASS` 要求原本失败的测试在修复后通过，用来证明需求已经解决；`PASS_TO_PASS` 则要求原本通过的行为继续通过，用来约束回归。这个结构把“看起来像修复”改造成“指定问题被修复，同时旧行为没有被破坏”。

这篇论文适合反复阅读任务构造部分。真实 Issue 往往描述不完整，仓库也包含大量无关上下文。Harness 必须固定初始状态、依赖、运行命令和评分逻辑，才能把自然语言任务转成可重复实验。后来对 SWE-bench Verified 的审计也说明，测试本身可能过窄、过宽或与描述不一致；任务集不是天然真理，也需要持续校验。

## 4. SWE-agent：工具接口也是模型能力的一部分

**论文：** [SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://papers.nips.cc/paper_files/paper/2024/hash/5a7c947568c1b1328ccc5230172e1e7c-Abstract-Conference.html)

SWE-agent 提出了 Agent-Computer Interface，也就是为模型设计的计算机交互界面。论文的核心判断很朴素：人类使用合适的 IDE、终端和调试工具会表现得更好，Agent 也有自己的使用习惯与限制。不能把人类工具原样暴露给模型后，就把所有失败归因于模型能力。

为 Agent 设计的接口需要让导航、查看、修改和测试动作更明确，输出更紧凑，错误更容易恢复。工具返回一大段无结构日志，和返回带文件、行号、错误类别与下一步建议的结果，对同一个模型来说并不是同一道题。

这篇论文让我在比较模型之前先比较接口：两个系统即使使用同一个模型，只要搜索命令、编辑协议、上下文截断、错误信息或重试策略不同，最终表现就可能不同。所谓“模型会不会写代码”，在 Agent 场景里往往已经是模型、接口和环境共同产生的结果。

## 5. OpenHands：Harness 需要成为可替换的平台层

**论文：** [OpenHands: An Open Platform for AI Software Developers as Generalist Agents](https://arxiv.org/abs/2407.16741)

OpenHands 把 Coding Agent 所需的能力组合成开放平台：Agent 可以写代码、操作命令行、浏览网页，在沙箱环境里执行任务，还能接入不同 Agent 和评估基准。它把“某个模型的一段循环”提升为一个可以替换模型、工具、运行环境和评估方法的系统边界。

这篇论文值得与 SWE-agent 对照阅读。SWE-agent 更强调接口如何改变单个 Agent 的行为，OpenHands 更强调如何把接口、执行、隔离、多 Agent 协作和 Benchmark 组合成平台。前者帮助我打磨一把工具，后者帮助我理解工具应该插入哪一层。

对实际项目而言，这意味着不要把所有逻辑锁在一个不可观察的循环里。任务定义、模型适配、工具协议、沙箱、事件记录和评分器应该有清楚边界。只有这些部件可以替换和独立验证，团队才有可能定位失败来自模型、Harness、测试还是基础设施。

## 6. Effective harnesses for long-running agents：跨上下文工作依靠交接，不靠记忆

**原文：** [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

长任务最容易暴露对话式编程的局限。上下文窗口会耗尽，新会话也不会天然继承上一轮的理解。Anthropic 把问题类比为轮班工程师：每个人开始工作时都不记得前一班发生了什么，所以系统必须留下可靠交接物。

文章采用 initializer Agent 和 coding Agent 两阶段结构。前者建立环境、功能清单与初始状态，后者每次只推进一个功能，运行端到端测试，并留下进度文件和 Git 记录。功能清单一开始全部标记为失败，后续 Agent 只能在真正验证后修改状态，从而减少“半成品被误认为完成”的机会。

值得反复读的是它对进度粒度的处理：一次只完成一个可验证切片，结束时让仓库保持干净、可恢复，并为下一轮留下结构化事实。长时间运行不是让同一个会话无限延长，而是让多次有限会话能够可靠接力。

## 7. Terminal-Bench：任务应该连同环境一起交付

**项目：** [Introducing Terminal-Bench](https://www.tbench.ai/news/announcement)

Terminal-Bench 把终端任务封装成自包含目录：Dockerfile 或 Compose 文件负责环境，`task.yaml` 描述任务，参考解法记录已知路径，测试文件判断最终状态。Harness 负责调度、执行、记录日志并收集评分。

这种组织方式的价值，在于任务不再只是 Prompt。一个终端任务还包含操作系统、依赖、文件、网络、资源限制、超时和测试入口。缺少其中任何一项，都可能让同一任务在不同机器上变成不同问题。

我会把这篇资料当作内部任务集的模板来读。团队可以把真实故障、迁移、配置和数据处理任务缩小后装进隔离环境，保留失败复现与最终断言。相比只收藏成功 Prompt，这类任务包更接近可以持续运行的工程资产。

## 8. Task-Completion Time Horizons：不要把运行时长当成自主能力

**研究：** [Task-Completion Time Horizons of Frontier AI Models](https://metr.org/time-horizons/)

METR 的 time horizon 不是 Agent 实际运行了多久，而是把任务难度映射到人类专家完成同类任务所需的时间，再估计 Agent 以 50% 或 80% 可靠性能够完成多长的人类任务。这个定义把“跑了六小时”和“能独立完成需要人类六小时的任务”严格区分开来。

这项指标值得反复读，因为长循环很容易制造自主性的错觉。Agent 可以长时间重复搜索、安装依赖或重试测试，但这些活动不等于有效进展。衡量长任务能力，需要固定任务集、评估成功概率，并把可靠性一起报告。

它也不应该被解释成替代人类工时的直接预测。任务分布、Harness、模型版本和人类基线都会影响估计。对团队更实用的做法，是借用这种思想：同时观察任务复杂度、成功概率和人工接管，而不是只记录 Agent 连续运行了多少分钟。

## 9. Agentless：复杂 Agent 之前，先建立简单基线

**论文：** [Agentless: Demystifying LLM-based Software Engineering Agents](https://arxiv.org/abs/2407.01489)

Agentless 有意去掉复杂的自主循环，把问题压缩成定位、修复和补丁验证三个阶段。在论文所用的 SWE-bench Lite 设置中，这个简单流程以较低成本取得了有竞争力的结果。具体分数依赖当时的模型、数据集和评估条件，今天不宜拿来做模型横向结论；它真正留下的是方法论上的反问：解决这个问题真的需要更复杂的 Agent 吗？

复杂系统拥有更多工具、记忆、规划和重试机会，也拥有更多失败点。没有简单基线时，团队很难知道新增一层规划器、记忆系统或多 Agent 协作究竟提高了成功率，还是只增加了 Token、时延和调试难度。

所以我会在设计 Harness 时保留一条最短路径：明确定位范围，生成有限候选，运行确定性验证。只有当真实失败样本证明它不够用时，再增加搜索、规划或协作。复杂度应该由证据推动，而不是由功能清单推动。

## 10. Quantifying infrastructure noise：Benchmark 测到的是整个系统

**原文：** [Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise)

这篇文章是清单里最重要的校准器。Anthropic 在保持模型、Harness 和任务集不变时，只调整 Terminal-Bench 2.0 的资源配置，最宽松与最严格环境之间的成功率相差 6 个百分点；严格限制下的基础设施错误率为 5.8%，不设上限时降到 0.5%。

资源不仅会制造随机失败，还会改变 Agent 可以采用的策略。内存充足时，它可以安装大型依赖或运行重型测试；资源紧张时，同一策略可能在写出代码之前就被 OOM 终止。因此，CPU、RAM、磁盘、网络、超时、并发和限制执行方式都不是 Benchmark 的背景信息，而是实验变量。

这篇值得放在最后反复读，因为它会改变对榜单小数点的态度。一个两三个百分点的领先，可能来自模型，也可能来自资源、基础设施稳定性或抽样波动。真正可比较的报告必须同时固定模型版本、Harness、任务集、预算、工具、资源和重试策略，并把 infra failure 与任务失败分开统计。

## 十篇文章共同指向一套什么系统

把这十篇资料串起来，我看到的不是十种互相竞争的方法，而是一条从任务到证据的因果链：

```text
可导航的仓库知识
  → 明确的任务契约
  → 适合 Agent 的工具接口
  → 隔离且可复现的执行环境
  → 小步、可恢复的工作循环
  → 确定性测试与质量评分
  → 成本、可靠性和人工介入的联合评估
```

模型决定系统能提出多好的候选方案，Harness 决定候选能否在边界内执行、能否得到真实反馈、失败后能否定位、成功后能否复现。Vibe Coding 的工程化，不是给 Prompt 再加一页规则，而是把原本依赖经验的判断逐步变成 Agent 可以看见、调用和验证的环境能力。

这也解释了为什么只看 `pass@1` 不够。一个 Harness 至少还要回答：每个被接受任务消耗多少 Token、费用和墙钟时间；首次有效补丁出现用了多久；重复运行的方差有多大；基础设施失败占多少；需要几次人工接管；修复后出现多少回归。为了准备上下文、启动沙箱和维护评估，Harness 本身又付出了多少成本？

我更愿意用三个组合指标观察它：

```text
每个接受任务成本 = 模型成本 + 基础设施成本 + Review 成本 / 接受任务数

净工程杠杆 = 人工基线工时 - 人工监督工时 - 返工工时

Harness 提升 = 同一批任务下新 Harness 成功率 - 基线 Harness 成功率
```

这些式子不是行业标准，而是根据十篇资料整理出的实践指标。它们的作用是迫使评估包含成本、人工和对照组，避免把“生成很多代码”误写成“工程效率提高”。

## 我建议的阅读顺序

如果第一次接触 Harness，我建议分三轮读。

第一轮先建立系统图：读 Harness engineering、SWE-agent、OpenHands。它们分别解释仓库怎样为 Agent 服务、接口为什么会改变能力、平台怎样组合执行与评估。

第二轮学习如何构造证据：读 SWE-bench、Demystifying evals、Terminal-Bench。重点不是记住榜单，而是看任务、环境、测试和评分器怎样组成可重复实验。

第三轮专门拆掉错觉：读 Effective harnesses for long-running agents、METR time horizons、Agentless、Quantifying infrastructure noise。它们会提醒你，运行更久不等于自主性更强，系统更复杂不等于效果更好，分数更高也不一定来自模型。

读完以后，不必立刻搭建完整平台。可以先选 30 到 50 个内部真实任务，写清初始状态、验收测试、回归测试、资源预算和失败分类。让当前工作流作为基线，每次只改变一项 Harness 设计，再重复运行并记录成本、成功率、人工介入与基础设施失败。真正稳定的改进进入回归套件，失败样本则继续指导仓库知识、工具和约束的建设。

这十篇文章最值得反复阅读的地方，正是它们不断把注意力从“模型这次写对了吗”移向一个更可操作的问题：我们有没有建立一套环境，让正确结果更容易出现、错误更容易暴露、改进能够被测量并复现？

## 资料范围与事实边界

本文的十项资料与筛选说明来自《AI 编程 Harness 深度研究：从 500+ 候选中筛选 Top 10》。写作前核对了 PDF 的五页内容，并复查了文中链接的主要原始来源，但没有重新执行 arXiv、OpenAlex 检索，也没有复现论文实验或项目 GitHub 关注度统计。

OpenAI 与 Anthropic 的工程文章提供了高价值的一手实践，同时带有组织环境和产品选择偏差；论文和公开 Benchmark 提供了可复查的方法，但其任务集、模型与基础设施条件也会过时。文中的三项组合指标和阅读顺序属于作者综合，不是来源原文的统一结论。
