# AI 工程进入系统时代：从 Agent 到 Harness、Loop 与 Skills

2023 年讨论 Agent，大家关心的是模型能不能规划任务、调用工具和独立完成工作。到了 2026 年，问题已经变了。Agent 能做事不再稀奇，难的是让它在真实项目里长期工作，同时保持可控、可查和可恢复。

Richard MacManus 在 [《5 Trends That Defined AI Engineering at World’s Fair 2026》](https://www.latent.space/p/aiewf26trends) 中总结了五个会议趋势：Harness Engineering、Loop Engineering、企业里的 Forward Deployed Engineer、Coding Agent，以及 Agent Skills。五个词指向同一件事：AI 工程正在从使用模型，转向建设一套围绕模型运行的生产系统。

## Agent 外面的系统开始决定上限

早期 Agent 原型通常由模型、Prompt、工具和一段循环代码组成。它可以演示自主执行，却很难直接进入生产环境。任务变长之后，系统必须处理更多问题：

- 本轮应该提供哪些上下文；
- Agent 可以访问哪些文件、数据和外部服务；
- 中断后如何恢复状态；
- 怎样判断输出合格；
- 失败后应该重试、换策略还是交给人；
- 模型升级后，原有流程是否仍然有效。

这些能力共同构成 Harness。模型负责推理和生成，Harness 负责把不稳定的模型行为限制在可管理的范围里。它包含上下文组装、权限控制、工具协议、状态保存、评估、日志和恢复机制，有时还要编排多个 Agent。

这和传统应用里的运行时很像。业务代码能表达功能，但生产质量还依赖数据库事务、权限、监控、重试和部署系统。模型能力越强，Harness 越不能省略，因为更强的模型能够执行范围更大的操作，也会放大错误的影响。

## Loop Engineering 设计的是反馈，不是死循环

让 Agent 一直运行很容易，写一个 `while` 就够了。困难在于每一轮是否真的更接近目标。

一种实用结构是把循环分成两层：

- 内循环由 Agent 执行任务，包括读取上下文、调用工具、修改文件和运行测试；
- 外循环观察内循环的结果，负责设定方向、评价质量、调整策略和决定是否继续。

外循环可以由人负责，也可以加入自动评估器。关键是评价标准不能完全交给执行任务的 Agent。让同一个 Agent 既写实现又宣布自己完成，类似让代码跳过测试直接上线，它可能给出有说服力的解释，却没有独立证据。

一个能进入生产环境的循环至少需要四类控制：

| 控制项 | 要回答的问题 |
| --- | --- |
| 完成条件 | 什么证据可以证明目标已经达成 |
| 停止条件 | 何时因为超时、重复失败或缺少权限而退出 |
| 风险边界 | 哪些操作可以自动执行，哪些操作必须批准 |
| 恢复机制 | 中断后从哪里继续，怎样避免重复产生副作用 |

传统控制循环面对的状态通常可测量、动作相对确定，Agent 循环则包含概率性判断。测试通过只能证明部分正确，评估器本身也可能误判。Loop Engineering 需要把确定性检查和人工判断安排在合适的位置，不能用“自主”替代控制。

## Coding Agent 改变了开发入口，但不会让 IDE 消失

代码补全时代的交互单位是一段代码。开发者负责拆解任务和组织上下文，AI 只预测接下来的几行。Coding Agent 把交互单位提高到了任务：它可以搜索仓库、修改多个文件、执行命令、根据报错继续调整，再把结果交给开发者检查。

开发者的时间因此从直接输入代码，逐渐转向三类工作：

1. 把模糊需求整理成目标和验收条件；
2. 为 Agent 提供项目规则、权限边界和必要上下文；
3. 审查实现、验证证据，并处理 Agent 无法决定的取舍。

这不等于 IDE 即将消失。代码浏览、断点调试、性能分析、局部编辑和可视化比较仍然重要。更可能发生的是 Coding Agent 成为任务层入口，IDE 继续承担精确操作，两者逐渐合并。Cursor 把 Agent 放进编辑器，Claude Code、Codex 和 Gemini CLI 从终端进入，Warp 又把终端改造成 Agent 工作区。界面还没有收敛，但任务级交互已经成为新的默认选项。

## Skills 是可以执行的团队经验

Skills 把任务步骤、工具用法、质量要求和常见失败模式写成 Agent 可以按需加载的文件。它比一段 Prompt 更接近可执行的团队规范。

比如，一个发布 Skill 不应该只写“帮我发布”。它需要说明发布前运行哪些检查、怎样更新版本记录、哪些文件不能提交、什么情况下必须停止，以及发布后用什么证据确认线上状态。资深工程师原本依靠经验完成的步骤，由此变成可以复用和审查的工作流。

Skills 也会带来维护成本。数量太多时，Agent 很难选对，多个 Skill 还可能给出冲突规则。模型升级后，旧 Skill 可能限制过度，也可能漏掉新能力带来的风险。因此，Skill 应该像代码一样管理：

- 每个 Skill 只解决边界清楚的一类任务；
- 记录适用条件，不要依赖含糊的自动触发；
- 用实际任务测试它能否稳定执行；
- 随模型、工具和项目规则变化及时更新；
- 合并重复能力，退役长期不用的 Skill。

“Agents are just files”很适合说明 Skills 的便携性，却不能解释全部生产问题。文件可以描述能力，真正执行时仍然离不开权限、运行环境、评估和审计。Skills 是 Harness 的一部分，不是 Harness 的替代品。

## 企业落地考验的是连接和治理

会议文章把 Forward Deployed Engineer（FDE）放在企业采用 AI 的中心位置。这个角色直接进入客户环境，把 Agent 接到内部数据、业务系统和团队流程里，并对最终 ROI 负责。

企业项目很少败在模型不会生成内容。常见阻力来自数据散落、权限复杂、流程没有统一定义、责任边界不清，以及结果无法衡量。一个演示里表现不错的 Agent，进入企业后必须回答更具体的问题：

- 它读到了哪些数据，依据是什么；
- 谁允许它执行写操作；
- 高风险变更由谁审核；
- 出错后能否定位到输入、模型、工具和规则版本；
- 部署团队离开后，客户能否继续维护；
- 节省的时间是否超过推理、集成和监督成本。

FDE 的价值在于同时处理软件集成和组织变化。这个角色能帮助早期项目落地，却不意味着企业采用已经成熟。会议参与者集中在模型公司、Agent 工具厂商和早期用户，他们看到的进展会快于普通团队。用会议趋势判断方向有价值，用它判断普及率则要谨慎。

## 五个趋势可以落成一套工程分层

把这些概念放进同一个系统，职责会清楚很多：

| 层次 | 主要职责 |
| --- | --- |
| Model | 推理、生成与工具选择 |
| Agent | 围绕目标组织单次或多次行动 |
| Skills | 提供可复用的工作方法和质量规则 |
| Harness | 管理上下文、权限、状态、工具和可观测性 |
| Loops | 根据反馈控制继续、纠偏、停止与升级 |
| Enterprise integration | 接入组织数据、业务流程、治理与 ROI |

团队不必一次建齐所有层。短任务可以从 Agent 加测试开始，重复任务再提炼 Skill，运行时间变长后补状态、预算和停止条件，进入企业环境之前再完成权限、审计和人工升级路径。自动化范围每扩大一步，验证与治理要同步跟上。

AI 工程师今后交付的不只是代码，也包括让 Agent 安全工作的环境：目标如何表达，上下文如何流动，能力怎样复用，错误在哪里被发现，风险何时交还给人。模型提供能力，工程系统决定这些能力能否稳定转化为结果。
