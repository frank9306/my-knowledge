# 我做了一个 Frontend Design Skill：让 AI 不只会写页面，还会做设计决策

让 AI 写一个前端页面并不难，真正难的是让它理解：这个页面服务谁、第一屏要完成什么、应该继承哪些现有规则，以及怎样证明最终界面真的可用。

这也是我做 [`frontend-design`](https://github.com/frank9306/agent-skills/tree/main/skills/frontend-design) Skill 的原因。它不是一套固定审美模板，也不负责把所有产品都改成同一种“高级感”；它更像一条前端设计工作流，把仓库调查、方向选择、工程实现、浏览器检查和结果交付连在一起。

它试图解决的核心问题很具体：**AI 生成前端时，缺的通常不是 CSS 能力，而是基于产品证据做取舍并验证结果的能力。**

## 为什么一句“做得好看一点”不够

常见的前端提示词会列出一些视觉偏好：简洁、现代、圆角、渐变、有动效。模型确实能据此快速生成页面，但这些词没有回答几个决定成败的问题：

- 用户打开页面时，最先要完成什么任务？
- 项目已经有哪些颜色、字体、组件和交互约定？
- 新页面应该延续现有产品，还是需要建立新的视觉方向？
- 加载、空数据、错误、权限不足等状态如何处理？
- 移动端、键盘操作、长文本和减少动效模式是否可用？
- 源码看起来合理之后，渲染结果由谁检查？

如果这些问题没有答案，AI 很容易回到统计意义上的安全默认值：居中的 Hero、两个按钮、三张同构功能卡、紫蓝渐变、玻璃面板、超大圆角和无处不在的 hover 动画。单个元素未必有错，问题是它们经常与产品内容、用户任务和既有设计系统没有因果关系。

所以这个 Skill 的第一条原则不是“更有创意”，而是**先确定谁有设计决定权**：用户明确要求优先，其次是仓库里的 `AGENTS.md`、`DESIGN.md` 和项目约定，再往后才是 Skill 提供的通用方法。对于成熟产品，同类页面和现有组件默认比一套外来的新风格更可信。

## 从提示词到可验证界面的六段闭环

![Frontend Design Skill 将仓库证据、任务路由、设计方向、实现和浏览器验证连接成闭环](/images/blog/frontend-design-skill/frontend-design-workflow.svg)

*概念插画：Skill 先读取项目证据，再选择任务路径、锁定方向、完成实现，并以真实渲染结果验证设计。*

### 1. 先读仓库，再谈设计

Skill 会先检查当前改动、运行时、包管理器、验证命令，以及 `AGENTS.md`、`DESIGN.md`、主题文件、全局样式、路由外壳、字体、图标和同类组件。对于改造任务，它还要求先说清楚当前界面究竟有什么可观察的问题。

这一步的价值在于把“设计上下文”从猜测变成证据。比如项目已经定义了 8px 间距基线、克制的 8px 圆角和蓝色语义 token，那么新增页面就不该随手引入 24px 圆角和另一套紫色渐变。若现有模式确实有问题，也应指出冲突并做最小范围修复，而不是借机重做整个系统。

### 2. 按任务路由，而不是一次塞满所有规则

前端任务并不只有“生成页面”一种。这个 Skill 把工作分成六条主要路径：

| 路径 | 典型任务 | 重点 |
| --- | --- | --- |
| Create | 新页面、新组件、新产品方向 | 设计理念、交互内容、响应式与无障碍 |
| Extend | 在成熟产品中增加新界面 | 设计系统、前端工程、响应式与无障碍 |
| Polish | 修复层级、排版、间距或视觉漂移 | 设计理念、视觉复核 |
| Screenshot | 根据截图还原或改进 | 先观察渲染证据，再加载对应规则 |
| System | 建立或更新设计系统与 `DESIGN.md` | token、系统演进、设计文档模板 |
| Review | 只审查、不改代码 | 视觉、无障碍与工程质量检查 |

另有一条 De-slop 路径，专门检查模板化视觉和文案；数据密集型界面则额外加载数据可视化规则。这样的拆分不是为了增加流程，而是为了减少无关上下文：做视觉审查时不必读取完整的设计系统模板，修一个已有组件时也不该自动发明新的品牌语言。

### 3. 在实现前锁定“视觉论点”

Skill 要求在大规模写代码之前确定七件事：用户与使用场景、页面的单一首要任务、视觉论点、内容层级、一个标志性元素、交互基调，以及框架、响应式、无障碍、性能和本地化等硬约束。

其中“视觉论点”不是“简洁现代”这种抽象形容词，而应能落到实现。例如：“高密度编辑工作台，使用墨色标题、低对比度分隔线和克制的朱红状态色。”这句话同时给出了密度、字体气质、表面关系和强调色边界，后续可以据此判断某个阴影、卡片或动画是否必要。

它还要求只把大胆用在一个地方。一个页面可以有鲜明性格，但不需要让字体、渐变、动效、3D 插图和异形布局同时抢夺注意力。对于工具型产品，“没有标志性元素”本身也可以是合理决定。

### 4. 把完整状态当成设计的一部分

很多 AI 页面只生成最顺利的静态截图，却没有加载、空数据、错误、禁用、权限不足和危险操作状态。这个 Skill 明确要求：只要流程可能到达，就应该设计那些会改变用户行动的状态。

工程规则也服从同一目标：组件保持单一且连贯的职责，状态靠近消费者，类型不能用 `any` 或强制断言掩盖。

对于 React，交互触发的逻辑放进事件处理器，独立请求并行执行，可重排列表不能用数组下标作为 key。Skill 不会强迫项目迁移到某个框架或组件库，而是先识别现有技术栈，再应用对应规则。

## “去 AI 味”不是删除某一种风格

Skill 的 `anti-slop.md` 收集了常见的模板化模式，例如渐变文字、氛围光斑、三张同构卡片、卡片套卡片、过量胶囊标签、`transition: all` 和没有产品含义的统计数字。

但这份清单不是禁用表。紫色渐变可以是品牌资产，玻璃表面也可能与产品环境一致。正确的判断顺序是：先找出这个视觉模式试图表达的产品决定，保留有依据的品牌选择，删除没有作用的装饰，再从内容、字体、间距和结构中重建层级。

换句话说，去掉“AI 味”并不等于换一套流行风格，而是让每个显眼决定都能回答“为什么它适合这个产品”。

## 源码检查不能替代浏览器

Skill 附带的 `scripts/verify-design.mjs` 会扫描前端源文件，提示几类值得复核的模式：

- `transition: all`；
- 渐变裁剪文字；
- 移除 outline 但没有明显 focus 上下文；
- 缺少 `alt` 的图片；
- 重复的 bounce、pulse、spin 动画；
- 常见的紫蓝默认渐变；
- `DESIGN.md` 是否缺少建议章节。

这些结果被刻意定义为 review leads，而不是自动判错。扫描器发现一个渐变，只能证明源码里出现了对应模式，不能证明它不适合产品。

同样，lint 和 build 通过也不能证明文字没有溢出、焦点环没有被裁掉，或手机上的弹窗不会被虚拟键盘遮住。

因此最终证据必须来自真实渲染：

- 检查项目支持的断点，并默认覆盖 375px；
- 使用键盘走一遍关键交互；
- 测试 hover、focus、pressed、disabled、loading、empty、error 和 success 状态；
- 检查控制台、溢出、临界换行、长文本、本地化扩展和 `prefers-reduced-motion`。

**源码负责提供线索，浏览器负责回答界面实际上发生了什么。**

## Skill 与 DESIGN.md 各自保存什么

这个 Skill 把方法和项目事实分开保存：

- Skill 保存可复用的方法：如何调查、如何选择路径、如何锁定方向、如何实现和复核。
- 项目的 `DESIGN.md` 保存本地决定：颜色 token、字体角色、间距、圆角、组件状态、响应式规则、内容术语，以及明确的 Do / Don't。

这种分工很重要。全局 Skill 不应该知道某个产品的主色、卡片圆角或品牌语气；项目文档也不必重复一整套通用设计方法。当 Agent 进入新仓库时，它带着同一套工作流程，却从仓库证据中得到不同的设计答案。

## 怎样使用这套 Skill

将仓库里的 `skills/frontend-design/` 安装到 Agent 可读取的 skills 目录后，可以直接用自然语言描述任务。例如：

```text
使用 frontend-design，重做这个 SaaS 的账单页。
保留现有组件库与品牌色，重点解决信息层级、移动端表格和失败状态。
完成后在 375px 和桌面宽度下检查，并报告浏览器验证证据。
```

对于现有项目，最好同时提供或维护一份 `DESIGN.md`，并保留真实截图、测试命令和可运行环境。输入证据越完整，Agent 越少依赖通用默认值。

当前版本仍有清晰边界：静态脚本只负责提示风险，不会理解全部视觉语义；Skill 可以要求浏览器验证，但前提是执行环境能够启动页面；它也不会代替产品研究，缺少真实用户与业务约束时，视觉论点仍然只能是带假设的工程判断。

这套 Skill 最终想建立的不是一种固定风格，而是一种可追溯的工作方式：先从产品与仓库找到依据，再做明确选择，把选择落实到完整状态和工程代码里，最后用真实渲染检查结果。这样，AI 交付的就不只是“看起来像页面”的代码，而是一份能够解释、继承和验证的前端实现。
