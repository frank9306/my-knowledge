# Harness Engineering 深度解读：当 AI 写代码，工程师应该设计什么

AI 编程最容易被误解成一道产能题：模型一次能生成多少代码，Agent 一天能提交多少 PR，团队能不能减少手写代码。OpenAI 的 Harness Engineering 案例真正值得关注的地方，却不是“100 万行代码”，而是这支团队为了让 Agent 持续工作，重新设计了代码库、工具、验证机制和人的职责。

在这个体系中，模型只是执行者。决定系统能否长期运行的，是模型周围那套让意图可读取、边界可执行、结果可验证、错误可回收的工程环境——也就是 Harness。

本文以 deusyu 整理的 [《Harness Engineering 概念总览》](https://github.com/deusyu/harness-engineering/blob/main/concepts/00-overview.md) 为线索，并对照 Ryan Lopopolo 发布于 OpenAI 的一手案例 [《Harness engineering: leveraging Codex in an agent-first world》](https://openai.com/index/harness-engineering/)，解释六个概念之间的因果关系、落地方式和适用边界。

## 先看清案例证明了什么

OpenAI 团队报告称，他们从一个空 Git 仓库开始，在五个月内由 Codex 生成约 100 万行代码。三名工程师推动了约 1500 个 PR，平均每名工程师每天 3.5 个 PR。

产品拥有内部日常用户和外部 Alpha 测试者，团队估算开发耗时约为人工手写代码的十分之一。代码、测试、CI、文档、可观测性和内部工具也都由 Codex 生成。

这些数字证明了一件有限但重要的事：在高度定制的工程环境里，Agent 可以承担远超“代码补全”的工作，并贯穿需求实现、测试、评审、修复和合并。

它们没有证明三件事：

- 代码行数等于产品价值或软件质量；
- 任何团队接入 Codex 都能复制相同吞吐量；
- 人类已经退出软件工程。

OpenAI 原文主动强调，这种端到端行为高度依赖特定仓库的结构和工具投入，不能假定它会自动泛化。所谓“零手写代码”，改变的是人类介入的位置：工程师仍在确定优先级、把用户反馈转成验收标准、设计约束并判断结果，只是不再亲手输入最终代码。

## Harness 不是一个工具，而是一套控制系统

“Harness”原意是挽具、线束或控制装置。放到 AI 编程中，它不是某个 Plugin、Skill 或命令行工具的专名，而是 Agent 周围所有可复用控制条件的总和：

- Agent 从哪里获得项目事实；
- 它能调用哪些工具；
- 架构允许哪些依赖；
- 什么结果算完成；
- 错误如何被发现；
- 失败后如何修复或升级给人类；
- 经验如何沉淀，避免下一次重复犯错。

因此，可以把可靠的 Agent 工作抽象为：

```text
意图 → 可读上下文 → 受约束执行 → 可观察结果 → 机械验证 → 反馈与修正
```

提示词只覆盖“意图”的一部分。只给 Agent 一段长提示词，却不给它稳定文档、统一命令、测试、日志和结构约束，相当于告诉驾驶员目的地，却没有道路、仪表盘和护栏。

## 六个概念其实是一条因果链

`00-overview.md` 将官方案例重组为六个概念。这种整理很有价值，但要注意：六项并不是彼此独立的最佳实践，而是逐层建立可靠性的因果链。

### 1. 仓库是 Agent 能看见的组织记忆

人在开发时会利用大量仓库之外的信息：会议结论、聊天记录、口头约定，以及“大家一直这么做”的隐性知识。Agent 无法稳定访问这些信息。即使工具允许读取 Slack 或 Google Docs，外部信息也可能缺乏版本、与当前代码状态不一致，或者无法在 CI 中验证。

所以“仓库即记录系统”并不是要求所有组织沟通都发生在 Git 中，而是要求会影响实现和验收的事实，最终进入可版本化、可链接、可审查的仓库工件。例如：

- 架构决策进入 ADR 或设计文档；
- 任务目标进入执行计划和验收标准；
- 常见故障进入运行手册；
- 代码边界进入结构规则；
- 重复工作进入脚本或 Skill。

关键不是“文档更多”，而是同一事实应有明确的权威位置。否则，Agent 会在多个互相冲突的说明之间猜测，团队也无法判断它依据的是哪个版本。

### 2. `AGENTS.md` 应该是地图，不是百科全书

把知识搬进仓库后，第二个问题随即出现：如果把所有规则都塞进一个巨大指令文件，上下文窗口会被低相关内容占满，重要约束反而更难被识别；文件越大，维护和验证也越困难。

OpenAI 团队因此把约百行的 `AGENTS.md` 当成目录，让它指向 `ARCHITECTURE.md`、设计文档、执行计划和其他更具体的事实来源。这就是渐进式披露：Agent 先获得小而稳定的导航，再根据任务加载相关细节。

好的地图至少回答四个问题：

1. 当前仓库是什么，边界在哪里；
2. 安装、运行和验证的标准入口是什么；
3. 哪些规则始终适用；
4. 遇到架构、测试、发布等问题应该继续读哪里。

地图不能代替道路。`AGENTS.md` 中写着“遵守分层架构”，却没有架构定义和检查方式，这条指令仍然无法可靠执行。

### 3. 把重要边界从文字提醒变成机械约束

自然语言适合表达意图和权衡，不适合独自守护高频不变量。Agent 可能漏读规则、误解规则，也可能在局部代码中复制一个已经存在但不正确的模式。

OpenAI 案例采用固定业务域分层：

```text
Types → Config → Repo → Service → Runtime → UI
```

依赖只能向前流动，认证、遥测和 Feature Flag 等横切能力通过明确的 Provider 接口进入。真正提供可靠性的不是这组层名，而是自定义 linter 和结构测试会拒绝非法依赖。

这体现了 Harness Engineering 的核心分工：

- 文档解释为什么，以及遇到例外时如何决策；
- 类型系统、lint、测试和 CI 判断一条具体变更是否越界；
- 错误信息告诉 Agent 下一步怎样修复。

能被确定性检查的问题，不应反复交给模型猜。机械约束不仅减少错误，还缩短 Agent 的搜索空间。

### 4. Agent 可读性决定它能否独立排障

为人类开发者设计的系统，不一定对 Agent 友好。依赖安装需要点击图形界面、接口行为藏在私有服务、日志缺少结构、应用不能隔离启动，都会迫使 Agent 在关键环节等待人类。

“Agent 可读性”要求项目的重要状态能够通过文本、命令和稳定接口被观察。例如：

- 使用统一、非交互式命令完成安装、启动和测试；
- 错误输出包含文件、规则 ID、原因和修复方向；
- 日志和 Trace 采用可搜索的结构化格式；
- 每个 Git worktree 可以启动隔离实例；
- 依赖选择优先考虑稳定 API、文档和可预测行为；
- 浏览器行为可以由 Agent 驱动并生成截图或视频证据。

“选择无聊技术”不是保守主义口号，而是在降低环境的不透明度。只有 Agent 能观察系统，它才可能形成“执行—检查—修正”的闭环。

### 5. 吞吐量变化会改变等待与纠错的成本

当 Agent 的产出速度远高于人的审查速度，传统流程中的瓶颈会移动。OpenAI 团队使用短生命周期 PR、较少的阻塞式合并门槛，并在部分测试偶发失败时通过后续运行处理，而不是无限等待。

这条经验最容易被误用。它成立需要多个前提：

- 变更足够小，回退或后续修复成本低；
- 自动检查覆盖关键风险；
- 发布和观测机制能快速发现回归；
- 故障影响可控；
- Agent 有能力自行处理构建失败和评审反馈。

在支付、权限、数据迁移或安全边界上，错误成本可能远高于等待成本。此时，高吞吐量并不会自动证明“先合并再修复”合理。正确做法是按风险调整门槛，而不是复制某个团队的合并速度。

### 6. Agent 会复制模式，所以仓库需要持续垃圾回收

Agent 擅长沿用已有模式，这既是规模化的来源，也是熵增的来源。仓库里只要出现一个不理想的 helper、一种绕过边界的写法或一套重复结构，后续生成就可能继续放大它。

据 [OpenAI 官方案例](https://openai.com/index/harness-engineering/)，团队最初每周五用约 20% 的时间清理所谓 “AI slop”。后来，他们把偏好整理成可机械执行的“黄金原则”，再让后台 Codex 任务定期扫描偏差、更新质量评分并提交小型重构 PR。

这里的关键不是安排一个“清理 Agent”，而是建立闭环：

```text
发现重复缺陷
  → 提炼为规则
  → 编码为 lint、测试或共享抽象
  → 扫描历史偏差
  → 生成小型修复
  → 继续观察规则是否有效
```

技术债因此从偶发的大扫除，变成持续的小额偿还。人的判断被使用一次，然后通过仓库机制反复执行。

![工程规则从仓库进入 lint 与测试，再由 Agent 修复并持续清理偏差](/images/blog/harness-engineering-overview/rules-feedback-loop-labeled.svg)

## 真正的最小落地方案

大多数团队不需要从“零手写代码”开始，也不应先建设复杂的多 Agent 平台。一个项目可以按失败暴露出来的瓶颈逐步增加 Harness：

### 第一步：让项目事实可定位

保留一份短 `AGENTS.md`，写清项目边界、标准命令、禁止事项和深层文档入口。把架构决策、验收条件和运行知识放进仓库，并明确各自的权威文件。

### 第二步：让常见动作只有一条标准路径

为安装、开发、测试、构建和发布提供稳定命令。减少需要人工点击、复制隐含参数或依赖个人环境的步骤。

### 第三步：机械化最重要的三到五条不变量

不要一开始追求覆盖所有“代码品味”。先选择代价最高、出现最频繁的错误，例如非法模块依赖、未验证的外部输入、缺失超时、数据库访问越层或敏感信息进入日志。

### 第四步：让失败对 Agent 可解释

检查结果应说明哪里失败、违反什么规则、期望结构是什么。只有“exit code 1”的自动化，对 Agent 和人都不构成高质量反馈。

### 第五步：记录重复人工介入

如果工程师反复帮 Agent 查同一个命令、解释同一条规则或修正同一种错误，这不是“模型不够努力”，而是 Harness 缺少工具、上下文或约束的信号。把修复写回仓库，再观察人工介入是否下降。

## 这篇总览最重要，也最容易忽略的结论

`00-overview.md` 用“人类掌舵，智能体执行”概括全文。更精确地说，人类负责选择目标、定义边界和承担判断；Agent 负责在这些边界内执行、观察和迭代；仓库负责保存组织记忆；自动化负责把关键判断变成可重复的反馈。

因此，Harness Engineering 并没有降低工程纪律的重要性。它把纪律从“工程师是否逐行写得足够仔细”，迁移到了更高杠杆的位置：

- 知识是否可发现；
- 意图是否可检验；
- 架构是否可执行；
- 系统是否可观察；
- 风险是否决定流程；
- 坏模式是否会被持续回收。

模型能力还会变化，但这六个问题不会因为模型更强而消失。Agent 越能独立行动，团队越需要把隐性经验变成清晰环境，把一次性纠错变成可复用反馈。Harness 的价值，正是在这种转化中产生。

## 事实核查与阅读边界

- “五个月、约 100 万行代码、约 1500 个 PR、三名工程师、人均每天 3.5 个 PR、约十分之一时间、单次运行超过六小时”等数据来自 [OpenAI 官方案例](https://openai.com/index/harness-engineering/)，属于该团队对自身项目的报告和估算。
- “六大核心概念”来自 deusyu 的 [中文概念总览](https://github.com/deusyu/harness-engineering/blob/main/concepts/00-overview.md)，是对官方文章的二次组织，不是 OpenAI 原文的正式分类法。
- “约十分之一时间”没有公开的受控实验方法、质量基线或长期维护成本数据，不应外推为一般生产率结论。
- OpenAI 明确表示，当前效果依赖该仓库的专用结构和工具；多年尺度下的架构一致性，以及人类判断最有效的介入位置，仍在探索中。
