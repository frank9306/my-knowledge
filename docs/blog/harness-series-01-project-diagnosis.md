# Harness 实战（一）：先诊断项目真正缺少什么

一个项目需要补的通常不是更多提示词，而是任务控制环中缺失的事实、工具或反馈。建设 Harness 的第一步，是找到 Agent 在哪里不得不停下来等人。

## 一次失败任务比一份能力清单更有价值

假设你让 Coding Agent 修复“订单列表偶尔显示重复记录”。Agent 修改了组件去重逻辑，单元测试也通过了。部署前人工检查却发现：重复来自接口分页游标，而不是组件渲染。

表面看是 Agent 推理失误，实际上至少有四个 Harness 缺口：任务没有保存复现条件，仓库没有解释分页契约，Agent 无法观察真实接口响应，验收也只检查了单元测试。

OpenAI 的 Agent-first 工程案例把类似问题归因于环境设计：当 Agent 缺少工具或项目事实时，团队应当补充环境，而不是反复要求模型“更仔细”。这是一条项目建设经验，不表示所有失败都能靠 Harness 消除。[OpenAI：Harness engineering](https://openai.com/index/harness-engineering/)

诊断时应选择一项最近真实发生、过程记录相对完整的任务，按时间顺序回答：Agent 收到了什么、读取了什么、执行了什么、看见了什么、如何判断完成，以及人类在哪一步介入。不要从“项目有没有 AGENTS.md”开始，因为文件存在不代表里面的事实足够，也不代表 Agent 实际读取过。

## 六个检查面

### 目标：任务是否允许做出一致判断

检查目标、非目标、边界条件和风险是否明确。如果 Agent 必须猜测“顺手重构是否属于范围”“数据库迁移能否执行”，问题出在任务契约，而不是代码搜索能力。

### 知识：项目事实是否可发现

检查命令、架构边界、领域规则和历史决策是否进入仓库，并有稳定入口。`AGENTS.md` 项目强调把面向 Agent 的说明放进仓库并允许分层覆盖；它解决的是信息发现入口，不会自动保证内容正确。[AGENTS.md](https://agents.md/)

### 执行：动作是否稳定可重复

安装、测试、构建和启动是否有唯一的非交互入口？命令是否依赖某位工程师电脑上的全局工具？失败时是否返回可靠退出码？如果 Agent 每次都要猜脚本参数，执行面还没有形成。

### 观察：Agent 是否看得到软件行为

单元测试之外，还要检查 Agent 能否读取接口响应、结构化日志、页面状态或运行指标。无法观察行为时，Agent 只能把“代码已修改”误当成“问题已解决”。

### 验证：结论是否有独立证据

验收条件必须对应具体检查：哪些由类型、Lint 或测试裁决，哪些需要运行用户场景，哪些必须由人判断。执行者的一句“测试通过”不是证据；命令、退出码、最终状态和未验证区域才是。

### 沉淀：同类失败会不会再次发生

若同一种人工纠正出现两次，就应判断它该进入文档、规则、测试还是工具。一次任务修好只是交付；下一次不再依赖同样的人工解释，才说明 Harness 得到了升级。

## 用人工介入记录决定优先级

建立一张很小的表即可开始：

| 任务 | 介入时刻 | Agent 缺少什么 | 临时处理 | 应沉淀到哪里 |
|---|---|---|---|---|
| 修复分页重复 | 行为验证 | 真实接口响应 | 人工提供抓包 | 测试夹具与接口契约 |
| 修改登录页 | 执行前 | 权限边界 | 人工提醒 | 安全规则与审批条件 |
| 升级依赖 | 构建阶段 | 标准验证命令 | 人工补命令 | 项目 Manifest |

优先修复“高频且可机械解决”的缺口。偶发、低影响、必须依赖业务判断的问题可以继续由人处理。Harness 的目标不是消灭所有人工介入，而是把人的注意力留给真正需要判断的地方。

## 读者练习

选择最近一项失败或返工任务，画出六步时间线。只记录观察到的事实，不先归因于模型能力。最后挑一个最小改动：补一条项目事实、一个标准命令、一项行为检查或一个升级条件，并说明它如何减少下一次相同介入。
