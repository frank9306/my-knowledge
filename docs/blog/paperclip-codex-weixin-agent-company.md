# 在 Windows 上组建 Frank's Team：Paperclip 三岗协作实战

10 月 29 日，我在 WSL 和 Docker 里试过七个 Agent。到了 11 月 3 日，我把新试点整理为直接运行在 Windows 上的 **Frank's Team**：负责人、开发、QA 三个岗位，用知识站的一篇文章重写检验协作。

这次最关心的，是负责人派出的任务有没有被实际接收，开发是否读了上游材料，检查是否对应同一版产物，以及最后由谁决定接受。角色少了，需求、实现、独立检查和人工验收这些环节仍然保留。

截至 11 月 3 日本次收口，文章已走过 FRA-4 负责人派工、FRA-5 开发交付和 FRA-6 首轮独立审查与行为验收。QA 执行期间，监督已登记水印颜色不一致的问题；QA 完成并释放 UI 后，负责人读回固定产物、447 项业务文件指纹和两份 QA 报告，再交原开发修复。修复后的最终包仍待复验与负责人核对，主人接受和发布尚未执行。

## 三个岗位，保留四种判断

我把产品澄清、技术判断和交付统筹先合在负责人这一岗，开发负责产物，QA 兼独立代码审查。这个取舍适合目前一个项目、一个小任务的试点，不能据此推出“三个 Agent 对所有项目都最好”。

| 岗位 | 要交出的东西 | 不能替代的判断 |
| --- | --- | --- |
| 负责人／CEO 兼 CTO | 需求、验收标准、派工、风险与交接 | 主人是否接受；是否允许发布 |
| 开发工程师 | 文章、图片、精确差异、自检和恢复说明 | 独立审查是否通过 |
| QA 与代码审查 | 固定输入的审查意见、行为验证和缺口 | 开发实现和主人接受 |

Paperclip 中，开发和 QA 都向负责人汇报。我保留需求边界和最终接受的人工节点。组织图里三个人已经摆好，仍要检查任务和产物，才能知道协作是否发生。[Paperclip 官方组织文档](https://docs.paperclip.ing/guides/org/agents/)提供岗位与运行管理的说明；下面的截图来自本次实例。

## Windows 上的执行和观察两路

当前 Paperclip 直接运行在 Windows，保存公司、项目、任务和交接记录，通过 Codex 适配器启动执行。业务项目仍是已有的 `my-knowledge` 工作树，没有为文章另建分支或复制项目。

本次三岗模型配置回读均为 `gpt-6.1-sol`、推理设置 `low`。这只是本机有效配置记录，不是对所有账号可用模型的推荐。沿用已有订阅入口，没有为文章新增付费模型账户。平台与 CLI 在本机执行，不能据此说模型权重也在本机运行。

| 组件 | 本次版本 | 用途 |
| --- | --- | --- |
| Paperclip | 2026.1023.0 | 组织、任务和运行记录 |
| Codex CLI | 0.166.0 | 执行岗位任务 |
| Node.js / pnpm | 24.22.1 / 10.14.0 | 本机工具与站点构建 |
| Windows-MCP | 0.8.8 | 原生窗口、截图和桌面操作 |
| Playwright MCP | 0.0.84 | 网页观察、交互与断言 |
| Python / uv | 3.14.10 / 0.13.7 | Windows-MCP 运行环境 |

版本表来自本次安装与运行记录。网上的最新文档用于理解接口，不能反过来证明本机安装了什么。

![架构解释图：Windows内的Paperclip调度Codex，Codex访问项目与两个MCP，模型服务位于执行主机之外](/images/paperclip-agent-company/ft-v1-architecture.png)

*图 3｜精确关系示意。蓝线表示调用关系，虚线框表示本机运行范围；共享 Windows 用户不等于岗位系统权限已隔离。*

网页由 Playwright MCP 读取、交互和执行浏览器断言；原生窗口由 Windows-MCP 观察、切换及截图。MCP 是 Agent 调用工具的接口协议，不是另一个负责业务判断的岗位。工具来源分别核对了 [Windows-MCP 官方仓库](https://github.com/CursorTouch/Windows-MCP)和 [Playwright MCP 官方仓库](https://github.com/microsoft/playwright-mcp)。

浏览器复用主人当前已登录的个人 Profile，不导出 Cookie，不复制完整登录状态。每个新 MCP 客户端先创建或选定任务专用页，再导航本公司页面，保留原始标签页。本次 MCP 进程运行在登录会话内，仅回环监听。服务进程存在与能观察登录桌面是两件事，Session 0 的启动结果不能直接当作桌面可用证据。

## 两个执行槽，一个写入者，一套桌面

这三项限制分别解决不同问题：

- 每岗同时一个原生任务；新团队最多两个实际 Codex 执行槽。准备阶段保留了双槽占满的阻塞探针记录，不能仅用界面 running 数量证明限流。
- 同一业务项目同时一个文件写入者。本轮是开发；负责人准备完 Issue 后释放写入权，QA 在冻结版本上检查。
- 浏览器和桌面操作全局串行。三个岗位可以连接同一个浏览器，不代表有三份隔离的浏览器状态。

执行槽、项目调度和岗位约定不能混成一种“安全隔离”。当前保持 `workspace-write` 与自动审批，普通用户运行，没有沿用旧容器关闭保护的取舍。QA 不改业务文件、开发只改指定范围，首先是执行约定；共享 Windows 用户与工具入口，尚不能证明系统会强制拒绝一切越界操作。

Playwright 官方明确说明 MCP 不是安全边界。站点名单、岗位提示词和工具白名单都不能单独证明私人账号已被完全隔离。周期心跳关闭，任务指派和依赖完成的事件唤醒仍保留。权限不足、配额不足或外部动作结果不明时，停止依赖该条件的动作，保留证据，再继续独立工作。

## Skills 按岗装配，还要真的读得到

提示词说明职责，Skills 提供工作方法。团队把共同规则、岗位文件、流程与 UI 工具入口分开：先读共同规则和岗位，再按阶段读取流程、技能表和 UI 工具说明。

| 岗位 | 主要技能 | 在这次任务里的作用 |
| --- | --- | --- |
| 负责人 | route-work、manage-issues、check-delivery | 固定范围、维护 Issue、核对交付 |
| 开发 | implement-issue、write-articles、read-web-content | 读取就绪任务、重写文章、制作图文和自检 |
| QA | review-code、frontend-design、read-web-content | 固定差异审查、事实与真实页面验证 |

技能来源是 `agent-skills` 本地快照：源提交 `e69ac3d` 加既有未提交内容，Paperclip 记录固定版本映射与源哈希。不能将其写成“远端仓库已经发布完全相同版本”。当前复用共享 Codex home，通过岗位绑定与目录映射发现技能，也不能包装成每岗独立文件系统。

这部分确实出过故障。组织自检时，开发发现 `implement-issue` 无法实读；普通用户创建符号链接出现 `EPERM`。监督侧用 NTFS 目录 junction 连接既有固定快照后，开发在原任务续接，实读技能与模块门禁文件，核对入口和目标的 SHA256 一致；QA 随后独立补核。首次失败保留，这次补核也没有声称审计了全部技能的所有参考文件。

旧技能里的 `app-use` 指针由新团队 `UI-TOOLS.md` 明确覆盖为两个 MCP。纯文章没有新增业务运行行为，不为套用 TDD 虚构模块或单测；检查重点是正文、图片、链接、构建和页面。

## 首个业务任务，就是重写本文

负责人创建本地 `ISSUE-0039`，明确保留原 URL、发布日期、历史边界、图片要求及排除项；完成就绪核查后，业务父任务 `FRA-4` 把开发子任务 `FRA-5` 交给开发。

开发实际读取了上游派工、主人原始交接第 9–11 节、项目文档、Brain、现行 `DESIGN.md`、旧文、构建命令和已有差异。Brain 仍有较早视觉描述，当前设计已是“安静书房”；文章插图按现行规范继续采用蓝色工程知识卡。持久记录有助于续接，冲突时仍须识别来源与日期。

工作树里已有首页和主题改动，所以开发只取得目标文章、新增同主题图片、必要证据、本 Issue／索引和 README 生成区的写入权。准备基线保存七个相关文件的备份与哈希，不是全树备份，不能拿来覆盖其他工作。

![my-knowledge项目的真实文章任务：父任务统筹重写，开发子任务实施，组织自检单独保留](/images/paperclip-agent-company/ft-v1-project-tasks.png)

*图 4｜本公司项目与文章任务实拍，Playwright MCP 采集后裁剪脱敏。进行中状态仅代表采集时刻，不表示独立 QA 或主人已经接受。*

组织自检父任务 `FRA-1` 与开发 `FRA-2`、QA `FRA-3` 是另一组记录：合成输入实读、技能补核和两个 MCP 调用发生在那里，负责人已读取下游结果并汇总。自检一度出现 API 状态与完成记录漂移，后续监督留言后恢复；本次再读 API 为 done。这个变化需要留痕，更不能拿自检 done 充当本文验收。

本次开发交出正文、六张 PNG、来源、差异和日志后释放写入与 UI。负责人核对固定产物和 447 项业务文件指纹，再派 FRA-6 独立审查与行为验收，并实际读取两份报告。QA 报告判断该冻结版本 P0、P1、P2 均为 0；监督另行发现其余图的水印颜色与封面不一致，这不是 QA 独立发现。负责人将问题交回原开发，首轮把水印颜色统一为封面蓝色，保留文字、字重和透明度；该问题返修计数为 1/2，修复后复验尚待执行。组织自检故障不计入本文返修，同一问题最多两轮，不因换会话重置；两轮仍不通过就交回证据、影响与处理选择。

*图 5｜交付约定示意。橙色表示待执行或待决定，红色回路表示确认缺陷后的返修规则，不是已完成的验收记录。*

## 真正卡住执行的环境细节

新团队最初受控 shell 运行失败，后续补齐 Windows 基础环境变量、通过岗位 PATH 使用系统 PowerShell，并以 `login=false` 执行后，原任务有了退出码 0 的记录。是否执行到目标程序要看真实日志，不能只看参数里的绝对路径。

本次工作区完整路径较长，Windows PowerShell 5 的部分文件操作把实际文件报成不存在。核对后，用 Node.js 读取同一工作区，本地 Issue 脚本以 Windows 扩展路径运行。没有因此移动项目、删除文件或复制成另一份业务工作区。

准备记录也出现过中文被写成问号的编码缺陷。开发依据原有效派工局部纠正，再以 UTF-8 读回。复杂中文改用独立文件或结构化参数，避免把损坏文本继续当作交接契约。

首轮 QA 在本任务新建的安全临时 textarea 中，通过 Windows-MCP 输入含中文的合成文本；Windows Snapshot 读回后，再由浏览器逐字核对。随后清空字段，双路确认空值并关闭临时标签。两份报告记录该专项通过；它验证的是本次临时字段与标签的恢复，不能泛化为所有原生应用或整个系统都已验证。

工具同样需要回读结果。组织自检中，Windows 工具回执曾给出不准确的窗口标题，快速截图摘要也出现空窗口列表；负责人核对实际页面与图像后才确认目标。成功字段证明调用被接受，不能单独证明操作符合预期。

![本文在本机浏览器中的实际预览，正文、解释图与来源图注可见](/images/paperclip-agent-company/ft-v1-preview.png)

*图 6｜本轮文章预览实拍，Windows-MCP 采集后裁剪脱敏。预览不替代 QA 对桌面与手机行为的独立验证。*

## 历史微信和当前能力分开

原文 10 月 29 日记录的是七岗“服不服科技”、WSL／Docker 与个人微信桥接。当时文字、语音转写回信和会话续接是旧环境记录；容器 namespace 故障后关闭内层保护，也是当时特定环境的取舍。

11 月 3 日这轮没有查询或改动旧公司，没有将旧桥接切换给 Frank's Team，也没有新增微信消费者。旧桥接当前健康状态未核验。因此不把“手机发语音就能指挥新团队”列为当前能力。URL 保留 `weixin` 历史 slug 是为了保留地址，不构成新接入需求。

当前可说明的是新团队的岗位读取、原生派工、工具调用和原任务修复后续接。它们不能证明跨任务自动继承全部聊天，也不能证明新团队微信链路已跑通。

| 检查对象 | 当前记录 | 边界 |
| --- | --- | --- |
| 三岗与模型 | 本公司 API 和组织界面回读 | 不代表岗位系统隔离 |
| 组织自检 | 实读、技能补核、两个 MCP 调用已有汇总 | 不代表本文交付 |

| 主人接受与发布 | 尚未执行 | 提交、推送与发布另需授权 |

项目生产构建已经串联 README 同步、设计检查和首页场景检查：

```powershell
# 在已安装依赖的 my-knowledge 项目根目录
pnpm docs:build
pnpm docs:preview --host 127.0.0.1
```

预览以命令实际输出的本地地址为准，再打开原文章路径 `/blog/paperclip-codex-weixin-agent-company`。正文另运行 `check_draft.py`，图片检查 PNG 规格及链接。构建通过不能保证手机没有横向溢出。首轮 QA 在 1440×900 与 390×844 下核对六图加载、页面与表格边界、代码可读性和真实滚轮，保留了断言与截图；这些结果对应修复前固定版，不能直接替代本次更新后的复验。

检查要对应最终输入 SHA256。返修改了正文、图片或影响页面的配置，相关报告就要重跑。恢复前先比对当前文件，确认仍是本轮版本，只撤销精确差异，不整库回滚，不覆盖后续用户修改。

原开发现依据已发生的审查与行为报告收口正文，并修复监督指出的水印颜色。原 check_draft.py 的 exit 1 保留：五条为元信息与整表长度提示，QA 实读后给出解释；开发外链超时日志与监督四项 HTTP 200 证据也分别保留。截至本次收口，更新后的最终包仍待负责人核对和 QA 复验，负责人最终 check-delivery 尚未发生。人工接受、暂存、提交、分支、PR、推送与发布均未执行。
