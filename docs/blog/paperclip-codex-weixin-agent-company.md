# 七个 Agent，一家公司：我的 Paperclip 自部署实战

今天，我在自己的电脑里组建了一支七人 Agent 团队，给它起名叫「服不服科技」。总管叫怼总，产品叫问号，技术负责人叫拆台，测试叫找茬——公司还没正式接单，名字已经把职场气氛安排明白了。

我的目标很具体：提出一个项目改动，让总管组织讨论、安排开发、推动独立审查和测试，最后把能验收的成果交回来。等这套流程稳定，再扩展到研究、写作、运营和日常助理。

一天折腾下来，团队建好了，总管真实派过工，同一聊天在重启后续接成功，个人微信也能发送文字和语音、收到总管的文字回复。最大的收获是：**组织图只画出了谁向谁汇报，任务交接、执行权限和验证证据，才决定这家公司能干什么。**

![服不服科技在 Paperclip 中的真实组织图：总管怼总统一调度六个专业岗位](/images/paperclip-agent-company/organization.png)

*封面：本次部署后的真实组织图，由本人提供。七个岗位已经建立，图本身不代表业务交付已经完成。*

## 先确定：我要的是一个能协作的团队

我已经在试用聊天类平台，但这次最关心的是：谁接需求，谁负责拆解，谁真的执行，结果交给谁检查，重启之后还能不能继续。

[Paperclip 的官方项目](https://github.com/paperclipai/paperclip)提供 Agent 管理与工作协作能力。对我这次试点而言，它负责承载组织关系、任务分配、依赖和运行记录；Codex CLI 负责实际执行。选它，是因为我想验证这条协作链能否跑通。

这次的边界也先定好了：以个人门户站的持续迭代为试点；日常由总管统一接单；需求确认和最终验收由我负责。涉及发布、删除数据、修改授权等操作，仍需要相应授权。

## 七个岗位，先把交付物写清楚

我没有一口气设二十个角色。首期只保留研发交付中职责明显不同的七个岗位。

| 岗位 | 名字 | 主要交付物 |
| --- | --- | --- |
| 总管 | 怼总 | 任务安排、进度、阻塞处理、最终交付清单 |
| 产品设计 | 问号 | 需求 Issue、验收标准、必要的交互说明 |
| 技术负责人 | 拆台 | 实施方案、模块边界、风险与必要设计记录 |
| 全栈开发 | 码工 | 可审阅的代码差异、相关测试与实现说明 |
| 测试验收 | 找茬 | 用户行为验证、缺陷、未覆盖项和验收证据 |
| 代码审查 | 御史 | 针对固定差异的独立审查意见及复核结论 |
| 交付运维 | 稳住 | 可复现交付物、运行说明、部署与恢复方案 |

全员都允许怼人，但有一条共同规则：说出问题，给出理由，提出改法。聊天可以幽默，代码、需求和测试证据必须准确。不能用段子掩盖阻塞，也不能把“正在努力”写进验收结果。

我给码工设定的一句口头禅很适合整个团队：“先别夸我写完了，测试还没同意。”

流程则是：

```text
提出目标 → 总管接单 → 产品澄清 → 我确认需求
→ 技术评估 → 开发实现 → 独立审查与测试
→ 整理交付 → 我验收
```

小修复复用已有设计，大改动才先做技术方案。每个项目首期最多一个写入者，总体最多两个 Agent 实际执行。同一问题最多自动返修两轮，仍未通过就报告证据和可选处理方式。

七个人研究一个按钮，按钮也不一定就有上市资格。组织流程要能降低沟通成本，不能自己成为成本。

## 平台在本机，模型仍可以在远端

这次环境是 Windows + WSL Ubuntu + Docker，Paperclip 与原来的 LobeHub 分开部署。Paperclip 使用独立的数据目录和服务入口，避免两套平台互相影响。

本机实际使用的 Paperclip 镜像版本为 `v2026.1023.0`，Codex CLI 为 `0.163.0`。这些是本次验证的版本，不代表后续版本的配置完全相同。

运行关系可以分成两条链：

```text
网页 → Paperclip → 指定 Agent → 容器内 Codex CLI → 远端模型服务

个人微信 → WSL 微信桥接 → 怼总原有聊天 → Codex CLI
         ← 对应运行的文字回复 ←
```

这里的“本地 Codex”，指客户端和工具执行发生在本地部署环境，模型推理仍访问远端服务。自部署平台、在本地运行 CLI、在本机运行模型权重，是三件不同的事。

因此，也不必给七个岗位分别购买七套模型。我们复用了现有 Codex 登录，没有为这次试点新增付费模型 API Key；具体可用量仍受原账号权益和使用限制约束。

## 复用 Codex 登录，先分清三套身份

最开始我也以为，既然桌面上的 Codex 已经登录，Paperclip 应该能直接用。真正落地时，才发现有三套身份需要分别处理：

- **Paperclip 管理员身份**：管理公司、岗位和任务。
- **Codex 登录身份**：允许执行环境中的 Codex CLI 调用模型。
- **微信绑定身份**：决定桥接接受谁的消息、把回复发给谁。

这三套身份相互关联，但登录其中一个，不会自动登录另外两个。

Codex 官方文档区分 ChatGPT 登录和 API Key 登录，并介绍了无浏览器环境复用认证缓存的方法。凭据可能保存在文件，也可能进入操作系统凭据库，不能假定每台机器上都有一份可直接复制的文件。[官方认证说明](https://learn.chatgpt.com/docs/auth)

这次沿用了已验证的 Codex 登录接入路线，把认证材料放在部署环境的私有位置。文章和仓库都不保存登录令牌；后续迁移机器，也需要通过受保护通道处理凭据。

Paperclip 管理员授权也有一个小插曲：某个入口提示邮箱或密码错误，但 `localhost` 的 onboarding 页面已经处于登录状态。最后沿用这个入口完成了 CLI 授权，没有重置密码。

这件事提醒我：排查登录时，要先确认当前访问的是哪个主机名、哪个浏览器会话，以及哪一种认证。别让一个授权入口的问题，把所有密码都折腾一遍。

## 执行失败，未必是模型不会干

岗位创建后，第一次真实工具执行就被容器中的 namespace 权限限制挡住了。

这属于执行环境问题：Agent 能接收任务，也能生成回答，但内层沙箱无法完成需要的系统操作。增加角色提示词的篇幅，解决不了这个错误。

这次我针对七个试用 Agent 明确授权，关闭 Codex 内层沙箱和逐条审批，继续由 Docker 提供外层隔离。没有新增宿主机目录挂载，没有挂载 Docker socket，也没有给容器增加特权。

这是本次受限试用环境的取舍。放宽一层执行保护后，容器能接触的目录、凭据和网络范围就更需要核实。旧三人试用团队的授权，也不能直接套给新七人团队。

另一个容易混淆的地方是岗位独立性。七个角色有不同任务和会话，但当前仍共享容器身份与公司级 Codex 配置位置。**给御史写一句“只读审查”，并不会产生操作系统层面的只读权限。**

正式机器上，角色配置、工作目录、Skills 和权限还需要进一步拆分。开发可写、审查按需只读，最终要由系统账号、文件权限或容器边界落实。

## 仓库连接、项目路径、浏览器，是三类环境能力

部署过程中，我还遇到了 GitHub 连接窗口关闭、本机路径无法识别，以及浏览器验收被运行库阻塞的问题。它们都发生在同一套平台里，却不能用同一个办法解决。

**GitHub 连接器认证与容器中的命令行认证需要分别核验。**网页连接成功，不代表容器里的 `git` 或 `gh` 已具备相同权限；弹窗关闭，也不能直接推断成仓库权限不足。

**容器中的路径必须在容器内存在。**Windows 上能打开的项目目录，不会因为填进 Paperclip 就自动出现在容器里。需要明确项目副本或挂载关系，再把 Agent 的工作目录设为容器实际可见的路径。

**浏览器验收还依赖完整运行环境。**当天一次首页文案任务报告：独立审查、构建、Lint、设计检查与 11 项单测通过，但浏览器验收没有通过。单测需要 `NODE_ENV=test`；容器则缺少 `libglib`、`libnss3`、`libX11` 等浏览器运行库，已有 Chromium 也无法启动。

没有桌面和移动端截图，就保留这个缺口。我的决定是把浏览器环境和受限宿主机能力留到正式机器部署时补齐，当前不扩大宿主机访问范围。

## 怼总不回复，先查平台限制

中间还出现过一次：我发消息，团队没有回复。

排查发现，总管触及了 Paperclip 配置的每日运行次数上限。当时的上限是 16 次，随后按我的要求调整为 1000 次；六个专业岗位仍保留各自原有的限制。

平台运行次数上限、执行并发、模型订阅额度，需要分别看。把平台上限改大，不会增加模型服务的额度；界面显示多个运行处于 running，也可能包含等待执行槽的任务。

这次在实际 Codex 执行入口增加了锁，将总执行并发限制为两个。判断“为什么没人回复”时，应该分别检查任务是否触发、Agent 是否暂停、运行上限、执行槽和模型请求结果。

## 会话续接，靠同一个任务的实际记录证明

我没有仅凭 Agent 回一句“我记得”就宣布续接成功。

测试时，先在怼总的原生聊天中留下测试标记，再重启服务、发送继续请求。核对运行记录后，前后原生会话 ID 一致，后续回复也能引用之前的标记。

这证明了本次环境中，同一聊天的会话续接可用。它不能证明跨任务会自动继承全部记忆，也不代表桌面 Codex 的历史聊天会自动进入 Paperclip。

跨任务协作仍依靠项目文档和交接记录。每次交接包含目标、当前结果、相关文件、验证证据、风险和下一步负责人；下游需要实际读取这些产物。

本轮还验证了总管真实创建专业子任务，产品角色读取上游交接后回报。角色自检与派工测试都有记录，但这些仍不能替代真实业务需求的交付验收。

## 微信接入：接回原来的怼总

网页能用了以后，我又想把入口搬到个人微信。日常在手机上说一句，比打开电脑找聊天页面更顺手。

这次没有另建一个微信专用 Agent，而是在 WSL 里运行独立桥接，使用腾讯发布的 iLink 协议，把消息交给怼总原来的 Paperclip 聊天，再回传对应结果。这是本次实现的桥接服务，没有另装 OpenClaw。[腾讯官方协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md)

扫码只是绑定账号，后面还有几条必须落实的消息规则：

1. 只接受扫码账号的私聊，过滤其他来源、群消息和机器人回声。
2. 输入消息与轮询游标一起持久化，按消息 ID 去重。
3. 用确定性的 `clientRequestId` 投递 Paperclip，网络响应丢失后可重试。
4. 根据触发评论与运行的关联选择回复，避免把网页上的其他回复转给微信。
5. 回信使用对应的 `context_token`；发送结果无法确定时停止自动重发，留下待核对状态。

桥接使用专用系统账号和私有状态目录，认证文件权限设为 `600`。它只向外连接微信和本机 Paperclip，不增加公网入站端口，也不把凭据目录挂载给 Agent。

Paperclip 专用密钥可以单独撤销，但这个版本的用户密钥继承用户权限，不能把它描述成公司级权限隔离。密钥还设有有效期，需要保留续期和失效处理步骤。

服务启动时又踩了一次目录权限：新系统账号无法进入原先选用的用户家目录。最后把代码放到 `/opt/paperclip-weixin`，状态放到 `/var/lib/paperclip-weixin`，保留用户家目录的原有限制。

## 语音不支持，原来是桥接漏接了字段

文字回信成功后，我试着按住说话，却收到“暂时只支持文字”的提示。我当时就问：其他 Agent 都能处理语音，为什么这里不行？

查了腾讯官方类型定义，发现语音消息的 `voice_item.text` 可以携带转写。首版桥接只读取文字消息，漏接了这个字段。[官方语音字段定义](https://github.com/Tencent/openclaw-weixin/blob/main/src/api/types.ts)

修复之后，链路变成：

```text
微信语音 → 微信附带的转写 → 怼总原有聊天 → 文字回复
```

这次真实语音测试中，服务确实取得了转写，触发总管运行，并成功回信。没有新增语音模型账户，也没有把音频转交给另一家转写服务。

能力边界要说清楚：当前使用的是微信提供的转写，并非本地直接理解音频。字段允许携带转写，不代表每条语音一定有；未收到转写时，桥接会提示重发或用微信转文字后发送。回复目前仍是文字。

## 今天验收了什么，正式机器还要补什么

截至 2026 年 10 月 29 日，本次部署取得了这些实际证据：

| 验证项 | 本次结果 |
| --- | --- |
| 七个岗位与职责说明 | 已配置、回读并完成岗位自检 |
| 总管派工与专业交接 | 已验证真实子任务与上游产物读取 |
| 同一聊天重启续接 | 已验证前后原生会话 ID 一致 |
| 微信文字收发 | 已跑通，手机端确认收到且内容正常 |
| 微信语音转写与回信 | 已用真实语音跑通 |
| 桥接异常与恢复行为 | 8 项行为测试通过，服务重启检查通过 |
| 首页任务的浏览器验收 | 未通过，运行环境缺少依赖 |
| 岗位级系统权限隔离 | 尚未完成，正式机器继续落实 |

下一阶段先在正式机器上核验系统、Docker、网络和登录，再补齐浏览器与目录权限。之后连续完成三个经过我确认的小型 Issue，并补测一次失败返修、一次阶段交接后的重启续接，通过后再扩大任务量。

现在如果要改一个项目，我会先找怼总，把目标说清楚：

> 我想调整首页的介绍区域，让第一次来的访客知道我做什么。先和我确认目标用户、内容范围和验收标准，汇总需要我决定的问题。需求确认后，再组织技术评估、开发、独立审查和测试；交付代码差异与证据，先不提交或发布。

这句话给了总管推进工作的入口，也保留了我的决策节点。下一次需要验证的，是这支团队能否按照这些约定，交付一个真实的小需求。
