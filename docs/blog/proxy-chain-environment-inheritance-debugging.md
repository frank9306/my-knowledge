# 代理能连，浏览器却打不开：一次代理链路排障实录

最近在开发一个跑 RPA 任务的 CLI。执行器会启动浏览器做自动化操作，浏览器还需要挂上业务提供的代理。

原以为这只是一个普通的代理配置问题，没想到最后牵出了三层上下文：别人默认知道但没有说出来的前置代理、OCR 把密码字符认错，以及启动执行器的 AI 环境悄悄传下来的代理变量。

排完以后只剩一个感受：心累。

## 代理测试正常，浏览器却打不开

事情从同事的一句话开始：

> 这个代理在别的地方能用，就在你这里不能用。

我把代理配置进浏览器，确实打不开网页。但单独做连通性测试时，结果又是正常的。

这就很让人疑惑了：明明能连，为什么不能用？

后来回头看，这里的“连得上”其实很容易造成误导。端口可达、TCP 握手成功，或者一个简单的探测请求返回，都只能证明链路中的某一小段没有断。浏览器真正访问网页时，还要经过代理协议协商、用户名密码认证、目标站点连接以及后续数据传输。

所以：

> **连通性测试正常，不等于完整代理链路可用。**

我接着反复测试代理，发现它的表现很不稳定：有时能建立连接，有时又失败。这时问题已经不像是浏览器参数写错，更像是当前执行环境缺了什么条件。

## 原来还有一层没人提过的前置代理

我开始对比“别的地方能用”到底是怎么用的。

这一对比，终于看出了区别：正常使用场景并不是直接连接目标代理，而是先经过另一个固定代理，再去连接它。也就是说，真实链路是：

```text
客户端 → 前置代理 → 目标代理 → 出口
```

而我的执行器一直在尝试：

```text
执行器 → 目标代理 → 失败或不稳定
```

这时我才恍然大悟。问题不是“同一个代理为什么在我这里不能用”，而是我们口中的“同一个使用方式”根本不是同一条网络链路。

![缺少前置代理时的失败链路，与补齐前置代理后的正常链路对比](/images/proxy-chain-debugging/upstream-proxy-chain.svg)

*概念插画：目标代理依赖一条没有被明确说明的前置链路。*

我给执行器补上前置代理能力，再试，果然好了。

这件事最坑的地方，是双方各自掌握的上下文不一样：

- 同事知道这个目标代理必须先经过前置代理才能稳定连接；
- 但他不知道我的执行器原本没有“前置代理”这项能力；
- 我知道执行器会给浏览器配置代理，却不知道对方说的“能用”默认包含了另一层网络环境。

所有人说的都没错，但关键信息恰好落在了两个人认知的缝隙里。

## 一个小插曲：密码里的 `1` 变成了 `I`

前置代理加完以后，我又测了一组配置，结果还是不通，这次报的是认证错误。

认证问题嘛，大概率就是用户名或密码不对。我找回原始代理信息，对着看了一遍，没发现哪里写错。又看了一遍，还是觉得没错。

最后我把两份信息复制给 AI，让它帮忙逐字符比较。结果很快出来了：

> 密码里的数字 `1`，被写成了大写字母 `I`。

两个字符在某些字体里本来就很像，如果代理信息来自截图，再经过 OCR 提取，就更容易把 `1`、`I`、`l` 混在一起。

这种错误最折磨人的地方在于：人眼会按照自己以为的内容去读，越熟悉那串字符，越容易自动忽略差异。

以后再遇到类似认证错误，比起对着截图看半天，更可靠的办法是：

- 尽量从原始文本复制，不要把 OCR 结果当作可信源；
- 对 `0/O`、`1/I/l` 等易混淆字符做逐字符比较；
- 调试时只比较长度、字符位置或脱敏后的差异，不在日志和对话中长期暴露完整凭据。

## 第二个问题：前置代理把本地代理绕回了自己

本以为加上前置代理以后就结束了，第二个问题马上又来了。

我的前置代理来源比较固定。执行器启动时会检查两类配置：

1. Windows 系统代理；
2. 当前进程里的 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 等环境变量。

如果检测到其中一项，就把它作为连接目标代理时的前置代理。正常情况下，这个策略很省事：不用再重复配置，执行器可以直接复用当前机器的出口环境。

但当我给浏览器配置一个 `127.0.0.1` 的本地代理时，连接又报错了。

我先检查系统代理，没有。再看 Windows 用户环境变量，也没有。那这个“前置代理”到底从哪里来的？

看了一眼 AI 的运行环境，我大概明白了。

我的 Codex 是通过多开工具启动的。每个 Codex 实例都可以在启动时注入独立的代理环境变量，而这个实例恰好配置了一个本地代理。执行器又是由 Codex 触发的，因此会像普通子进程一样继承父进程的环境变量。

于是，虽然 Windows 的持久化环境配置里看不到代理，执行器自己的进程环境里却真实存在：

```text
多开工具
  └─ Codex（带有代理环境变量）
       └─ 执行器（继承同一组代理环境变量）
```

当浏览器配置的目标代理与继承到的前置代理，恰好都是同一个 `127.0.0.1:<port>` 时，链路就可能变成：

```text
浏览器请求
  → 本地代理桥
  → 准备连接目标代理
  → 检测到环境变量中的“前置代理”
  → 再次访问同一个本地代理
  → ……
```

代理桥原本想借助前置代理访问目标代理，结果前置和目标指向同一个端点，相当于“为了到达自己，先经过自己”。根据桥接实现的不同，它可能表现为递归转发、连接不断兜圈、认证上下文错位，最后以超时、连接失败或认证错误结束。

![Codex 子进程继承本地代理变量后形成自引用回环，以及识别本地端点后直连的修复链路](/images/proxy-chain-debugging/local-proxy-loop.svg)

*概念插画：同一个本地端点同时成为目标代理和前置代理时，会形成自引用链路。*

这里需要诚实说明：当时没有保留下完整抓包和代理桥逐跳日志，所以我不能百分之百证明每个失败请求都按这条路径循环。但三个现象能够互相印证：

- 执行器确实继承到了 Codex 进程的代理环境变量；
- 继承的前置代理与浏览器目标代理指向同一个本地端点；
- 对这个本地目标跳过前置代理以后，请求恢复正常。

因此，“同端点自引用”是与现象和修复结果一致的高概率根因。

最终处理也很直接：如果目标代理是本机回环地址，并且与检测到的前置代理是同一个规范化后的 `host:port`，就不要再套一层前置代理，直接连接目标代理。

注意，不能只凭“目标是 `127.0.0.1`”就无条件绕过。机器上可能同时运行多个本地代理，它们端口不同、职责也不同。真正需要拦住的是**前置端点与目标端点相同**的自引用情况；比较时还应统一处理 `localhost`、`127.0.0.1`、`::1`、默认端口和协议表示。

## 这一天真正让我学到的三件事

### 1. 隐含的网络前提必须显式化

“这个代理能用”不是一个完整描述。更有用的信息应该是：它从哪里连接、是否依赖固定出口、是否需要前置代理、使用什么协议、认证发生在哪一层。

网络问题经常不是某个组件单独坏了，而是两个人对“运行环境”的定义不一样。

### 2. 进程环境变量也是运行配置

检查代理时，不能只看 Windows 设置界面和用户环境变量。父进程临时注入的变量同样会被子进程继承，而且它们只存在于这棵进程树里。

从终端手动启动和从 Codex 触发，看起来运行的是同一个可执行文件，实际拿到的环境可能完全不同。

### 3. 自动代理检测必须防止自引用

自动读取系统代理和环境变量很方便，但“检测到了代理”只是第一步。真正使用前还要判断：

- 它是否与目标代理相同；
- 它是否指向当前代理桥自身；
- 本地回环地址是否需要绕过；
- 最终选中的链路能否被日志清楚地展示出来。

如果执行器一开始就输出“目标代理来自浏览器配置，前置代理来自父进程环境变量，两者解析后为同一端点，因此跳过前置代理”，这一天大概能少掉一半的折腾。

## 写在最后

回头看，这两个代理问题都不是多高深的网络原理。

第一个问题，是同事知道需要前置代理，却不知道执行器没有这项能力；第二个问题，是我知道自己没有配置系统代理，却忽略了 Codex 启动环境会把临时代理变量传给子进程。中间还夹着一个 OCR 把 `1` 认成 `I` 的小坑。

真正难排的往往不是代码，而是没人意识到自己漏说了什么。

心累的一天，至少最后把这几层“默认存在”的东西都翻了出来。
